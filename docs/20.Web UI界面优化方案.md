## 一、现状总览

当前 Web UI 是**零依赖、单文件**前端（vanilla JS + 手写 DOM，无框架、无构建、无测试），
由 `debug.py` 的 `http.server.SimpleHTTPRequestHandler` 静态托管在 `8020` 端口，
通过 ACP 协议与后端通信：

| 端点 | 方法 | 用途 |
|------|------|------|
| `/acp/message` | POST | 请求/命令（create_session、send_message、interrupt、resume_session、reply_user 等） |
| `/acp/events?session_id=` | GET (SSE) | 流式事件（phase_changed、llm_stream_chunk、final_answer、ask_user 等） |
| `/acp/sessions/{id}/messages` | GET | 拉取会话历史消息 |
| `/health` | GET | 健康检查 + 活跃会话数 |

**技术特征**：自研 Markdown 渲染（`simpleMarkdown`/`processInline`）、自研 SSE 解析
（`fetch`+`ReadableStream` 手动拆行）、`requestAnimationFrame` 节流 + 阶段卡片折叠、
30s 轮询刷新会话列表。

这套架构的优点是**部署极简**（单个 HTML 文件）；代价是健壮性、性能、可维护性、
安全性、交互体验五方面都存在短板，按优先级诊断如下。

## 二、问题诊断

> 每个问题标注 `[来源]`（20/21/23/新 四轮）+ 优先级。代码行号以 `web_ui/index.html` 为准。

### 2.1 P0 · 健壮性与交互死点（会「卡住/迷失用户」）

#### 2.1.1 SSE 生命周期不统一（解析不合规 + 无重连 + 回复后不重开）`[20-2.1.1/2.1.2 + 21-1.1]`

- **现状**：`readSSEStream`（`:662-696`）手动按 `\n` 拆行，只识别 `data:` 单行，不处理
  多行 `data:`、`\r\n`、`:` 注释行；无超时/重连；心跳 `{}` 被直接忽略。`submitReply`
  （`:1491-1518`）回复 ask_user 后**只 POST + 改状态，不重新打开 SSE**，依赖旧连接的
  「残留活性」。
- **问题**：网络抖动/后端重启时 SSE 静默断开，前端既不检测也不重连，界面永久卡在
  「执行中」；尤其 ask_user 等待期间断线后用户回答，**没有任何读取器监听**，事件全丢，
  界面空转。
- **建议**：收敛为「一次会话一条显式的 SSE 生命周期」——`sendMessage`/`resumeSession`/
  `submitReply` 共用同一条「开始读取 → 结束读取」路径；断线检测 + 自动重连；
  规范 SSE 解析（或改用原生 `EventSource`，见决策点 D1）。

#### 2.1.2 中文输入法 Enter 键误发送（致命）`[23-1.1]`

- **现状**：`handleKeyDown`（`:1358-1363`）与 ask_user 回复框 keydown（`:1470-1479`）
  只判断 `e.key === 'Enter' && !e.shiftKey`，**无 `e.isComposing` / `keyCode===229` 判定**。
- **问题**：中文输入法下按 Enter 确认候选词（如 `nihao`→「你好」）也会触发发送，
  **消息没打完就被发出**。对本中文项目，每个中文用户几乎每条消息都踩到。
- **建议**：两处处理器首行加 `if (e.isComposing || e.keyCode === 229) return;`。

#### 2.1.3 执行期间输入框被整体禁用 `[21-1.2]`

- **现状**：`updateSessionStatus`（`:912-913/917-918/922-923`）在 running/resuming/
  awaiting_user 三种状态都把 `#userInput` 置为 `disabled`。
- **问题**：Agent 长跑期间用户无法打字「预输入下一句」，被迫等→停→再等。
- **建议**：输入框始终可输入，仅 running 期间禁用**发送按钮**（视觉置灰 + 文案），
  `expired` 才真正禁用输入框。

#### 2.1.4 无「停止」按钮 + 「暂停」语义误导 + 发送按钮无语义 `[21-1.3 + 23-4.2]`

- **现状**：「⏸ 暂停」实际是 `interrupt`（`:933-945`，到安全边界才停，非即时）；
  无「停止生成」；发送按钮运行中仍是灰箭头 `&#10132;`（`:421`）。
- **问题**：长工具调用中点暂停可能等很久；想放弃本轮无路可走；运行中按钮无语义。
- **建议**：「暂停」改「请求暂停」并加暂停中态；**运行中把发送按钮复用为「停止」**
  （图标 ➢→■）；停止 = 取消 SSE + 发 interrupt + 回退可输入态。

#### 2.1.5 恢复执行「抹掉」过程 + 历史只显示最终答案 `[20-2.1.3 + 21-1.4]`

- **现状**：`resumeSession` 开头 `clearPhaseSections()`（`:954`）删除已渲染的阶段卡片；
  `switchSession`（`:1303-1312`）加载历史只渲染 `user_input`/`final_answer` 两类，
  中间的方案/工具/审核过程全丢。
- **问题**：暂停→恢复后用户刚看的方案「瞬间消失」；切走再切回只能看到最终答案。
- **建议**：恢复时保留已渲染阶段、只续新事件；按 `message_type` 完整还原历史阶段卡片。

#### 2.1.6 会话详情数据源不一致，空值访问风险 `[20-2.1.4]`

- **现状**：`switchSession` 用 `s ? s.preview : '会话'` 三元兜底（`:1334`），`s` 依赖
  `listSessions` 缓存，二者失败时序不一致时标题与列表错位。
- **建议**：统一「会话详情」单一数据源，消除潜在 null 访问。

### 2.2 P1 · 性能与流式阅读

#### 2.2.1 流式渲染 O(n²) 整体重写 `[20-2.2.1]`

- **现状**：`llm_stream_chunk` 每帧 `innerHTML = simpleMarkdown(buf)`（`:816`）整体重写，
  文本接近 50KB 上限时卡顿。
- **建议**：维护「已渲染游标」，只追加新片段（增量渲染）。

#### 2.2.2 流式输出的「半成品 Markdown」渲染错乱 `[23-2.1]`

- **现状**：`simpleMarkdown` 的代码块正则只匹配**闭合** fence（`:490`）。代码块已出
  `` ``` `` 而结尾未出时，中间帧把 `` ``` `` 当字面文本，内容反复「跳动/变形」。
- **建议**：与换 `marked` 合并处理——渲染前检测未闭合 fence，尾部未闭合段用 `<pre>` 包裹。

#### 2.2.3 会话列表每 30s 全量重建 DOM `[20-2.2.2]`

- **现状**：`renderSessionList`（`:1235-1259`）每次 `innerHTML` 重建整表，轮询（`:1594`）
  无条件触发，导致闪烁、焦点丢失、误触。
- **建议**：轮询前 diff（对比 session_id + updated_at），无变化不重建；交互中暂停刷新。

#### 2.2.4 无虚拟滚动 `[20-2.2.3]`

- 多会话/超长对话下 DOM 节点累积，滚动与内存退化。作为 P2 优化项，配合增量渲染一起做。

#### 2.2.5 强制滚动到底部，无视用户上滚 `[21-2.1]`

- **现状**：`scrollToBottom()`（`:1008-1013`）在多处（822/996/1005/1093/1169/1182/1430）
  每帧无条件 `scrollTop = scrollHeight`。
- **问题**：流式期间用户上翻看历史会被持续拉回底部，无法翻阅上文。
- **建议**：stick-to-bottom 判定（距底 `<40px` 才自动滚）；上滚后停止跟随并显示
  「↓ 回到底部」悬浮按钮（`21-2.2`）。

#### 2.2.6 阶段内容双重滚动条（max-height 限制）`[23-2.3]`

- **现状**：`.phase-body { max-height:2500px; overflow-y:auto }`（`:284`），长输出在卡片内
  嵌套滚动，与外层滚动冲突；外层自动滚到底、内层却未滚，用户误以为看到最新。
- **建议**：去掉 max-height，阶段内容随外层滚动（配增量渲染/虚拟滚动）。

#### 2.2.7 阶段完成即自动折叠，打断阅读 `[23-2.2]`

- **现状**：`completeCurrentPhase`（`:1103-1137`）在新阶段开始时把上一阶段折叠，用户
  正读的内容「在眼前塌掉」，被迫反复点「▶」展开。
- **建议**：默认阶段完成后保留展开（或保留最近 N 个），提供「全部折叠」主动按钮。

#### 2.2.8 流式输出 50000 字符「静默截断」`[23-2.4]`

- **现状**：`if (streamBuffer.length < 50000)`（`:799`）超限后 token 静默丢弃、无提示。
- **问题**：用户以为完整输出，实际被悄悄砍掉，还浑然不觉（欺骗性体验）。
- **建议**：达到上限立即插入醒目「⚠ 已截断」提示；更彻底改为可配置上限或后端分页/导出。

#### 2.2.9 消息无时间戳 `[21-2.3]`

- **现状**：仅会话列表有相对时间，消息气泡无任何时间信息。
- **建议**：消息悬浮显示时间戳，或相邻消息间隔 >10 分钟时插入时间分隔线。

#### 2.2.10 长代码块无「复制」按钮 `[21-2.4]`

- **现状**：代码块为纯 `<pre><code>`，最终答案也无复制入口。
- **建议**：代码块右上角复制按钮 + 最终答案「复制全文」（`navigator.clipboard.writeText`）。

### 2.3 P1 · 会话管理与反馈可视化

#### 2.3.1 会话标题全部显示「新会话」`[21-3.1]`

- **现状**：`renderSessionList` 用 `s.preview || '新会话'`（`:1245`），preview 常为空，
  列表一堆「新会话」难以区分。
- **建议**：前端兜底取首条 `user_input` 前 N 字作标题；可选后端 LLM 摘要（见 D4）。

#### 2.3.2 删除按钮常驻 + 原生 confirm `[20-2.4.3 + 21-3.2]`

- **现状**：删除按钮常驻列表（`:1253-1255`），点后弹 `window.confirm`（`:645`）。
- **建议**：删除按钮 hover 显示（或收进「…」菜单）；自定义确认弹窗（带标题 + 不可撤销）；
  可选「撤销删除」Toast。

#### 2.3.3 缺失重命名 / 搜索 / 排序 `[21-3.3]`

- **现状**：无重命名、无搜索、按后端返回顺序渲染（活跃会话可能沉底）。
- **建议**：列表顶部加搜索框；按 `updated_at` 降序；会话项加重命名入口。

#### 2.3.4 输入草稿不持久 `[23-1.2]`

- **现状**：textarea 的 `input` 只做 autoResize（`:1551-1557`），草稿不写 localStorage。
- **建议**：按会话存 `ga_draft_<sid>`，切换/刷新/新建时保存与载入，发送成功清除。

#### 2.3.5 活动会话不持久化，刷新回空状态 `[23-3.2]`

- **现状**：仅 `BASE` 存了 localStorage（`:549/1533`），`activeSessionId` 未持久化。
- **建议**：存 `ga_active_session`，`init` 时自动 `switchSession` 恢复。

#### 2.3.6 刷新/关闭无「离开保护」`[23-3.1]`

- **现状**：无 `beforeunload`。执行中或草稿未发送时误刷新/关页，执行中断、草稿丢失。
- **建议**：执行中或有草稿时注册 beforeunload 挽留，结束后移除。

#### 2.3.7 用户消息无「编辑重发」`[23-1.3]`

- **现状**：用户消息发出后不可编辑/重发。
- **建议**：用户气泡 hover 加「编辑」（回填重发）与「重新发送」（先按新一轮实现成本最低）。

#### 2.3.8 发送后无 typing 指示 `[21-4.1]`

- **现状**：`sendMessage` 后到首个 phase 事件前，仅状态点变蓝，无「Agent 正在思考」反馈。
- **建议**：插入三点动画气泡（`aria-live`），收到首事件移除。

#### 2.3.9 错误反馈「一闪而过」`[21-4.3]`

- **现状**：`addEvent('error')`（`:999-1006`）插一条居中 event-card，随即被滚动冲走。
- **建议**：错误/告警走持久 Toast（右上角，可关闭），过程性信息继续走消息流。

#### 2.3.10 连接状态感知弱 `[21-4.4]`

- **现状**：`checkHealth`（`:1375-1386`）只更新底部小状态点，断线难察觉。
- **建议**：断线顶部横幅「连接断开，正在重连…」，恢复短暂提示。

#### 2.3.11 工具/阶段信息可视化不足 `[21-4.2 + 20-阶段五-4 + 新]`

- **现状**：`tool_call` 只显示工具名，返回截断 200 字符（`:777`），参数/风险等级不展示；
  更关键的是 `phase_changed` 的 **`detail` 字段被前端丢弃**——后端每个阶段都发了
  `detail`（子任务描述 `task_description[:120]`，`subagent.py:127`），但前端
  `createPhaseSection(label, agentName)`（`:1020`）只收 label/agentName，`detail` 读了
  却从不渲染（`:755`）。
- **问题**：多子任务并行时，用户看到的是一排 `执行子任务 [task-1] · skill名` 卡片，
  **task_id 透明、任务描述丢失**，完全不知道每个子任务在做什么。
- **建议**：工具卡片展示参数 + 风险等级徽章 + 返回可展开；`createPhaseSection` 增加
  `detail` 参数，渲染为阶段标题下的说明行（本项修复成本极低、信息收益高）。

### 2.4 P1 · 安全与可访问

#### 2.4.1 Markdown 渲染存在 XSS 风险 `[20-2.4.1]`

- **现状**：`simpleMarkdown` 先 `escHtml` 但 blockquote 分支依赖转义后 `&gt; ` 匹配、
  代码块占位符 `\x00CODE{n}\x00` 在转义后替换、无链接协议校验，存在脆弱注入路径。
- **建议**：替换为 `marked` + `DOMPurify`（渲染后消毒），根治 XSS 并解锁表格/任务列表/图片。

#### 2.4.2 无安全响应头 `[20-2.4.2]`

- **现状**：静态托管默认不设 CSP、`X-Content-Type-Options`、`X-Frame-Options`。
- **建议**：托管层加最小 CSP 与安全头。

#### 2.4.3 可访问性不完整 `[20-2.4.4]`

- **现状**：阶段卡片展开/折叠仅靠点击 div，无 `role="button"`/键盘触发；焦点管理缺失；
  状态点仅靠颜色区分。
- **建议**：补 ARIA 与键盘触发、完善焦点管理、状态加语义文本。

### 2.5 P2 · 可维护性

#### 2.5.1 大量 `!important`「补丁式」CSS `[20-2.3.1]`

- **现状**：末尾「最终强化修复样式」（`:340-363`）用 `!important` + `position:static` 等
  暴力覆盖，`.phase-section` 定义两处重复（`:211` 与 `:351`）。
- **建议**：重构为稳定 Flexbox，删除补丁段，关键类只保留一份定义。

#### 2.5.2 魔法数字与竞态 hack `[20-2.3.2]`

- **现状**：`setTimeout(80)`（`:767`）、`setTimeout(30)`（`:1023`）、`50000`（`:799`）、
  `200`（`:777`）、`30000`（`:1594`）散落；`domRenderLock` 用 while+setTimeout 轮询。
- **建议**：抽出阶段渲染状态机，事件驱动替代竞态 hack，魔法数字提为具名常量。

#### 2.5.3 三个职责重叠的清理函数 `[20-2.3.3]`

- **现状**：`resetChatPhase`（`:1185`）/`clearPhaseSections`（`:1208`）/`clearChatMessages`
  （`:1262`）职责重叠，调用时机易混，是 2.1.5「恢复清空」的温床。
- **建议**：合并为 `resetView()`，明确「发送前」与「切换会话」两种语义。

#### 2.5.4 调试日志未清理 `[20-2.3.4]`

- **现状**：`console.log('[API] request...')` 等散落，生产泄露请求/会话细节。
- **建议**：封装可开关 logger，默认关闭。

#### 2.5.5 阶段标签映射不一致，`任务执行` 为死代码 `[新]`

- **现状**：`PHASE_ID_MAP`（`:562-569`）硬编码 6 个中文阶段，但 SubAgent 层实际发送
  `子任务执行`、`执行子任务 [task_id]`、`执行第 N 层` 动态标签，不在映射内，
  走 slug 兜底（DOM id 带方括号）；`任务执行` 映射项后端从不发送（死代码）。
- **问题**：前端阶段体系与后端脱节，脆弱。
- **建议**：统一前后端阶段命名/枚举，或用「固定阶段 + 动态任务」两级模型。

## 三、优化路线图

### 3.5 决策点（需产品/团队拍板）

| 编号 | 决策 | 选项与影响 |
|------|------|------------|
| D1 | SSE 实现 | A) 原生 `EventSource`（自动重连、代码少，需处理 `onerror`+未读补偿）；B) 保留 fetch+手写重连（可控、代码多）。**倾向 A**。 |
| D2 | Markdown 方案 | `marked`+`DOMPurify` vs 继续自研。「零依赖」是现状卖点，但安全成本已高于收益，**倾向引入**。 |
| D3 | 是否引入构建工具 | 当前「单文件零依赖易部署」是卖点。建议**至少 HTML/CSS/JS 拆分 + 按职责分模块**，是否上 Vite/TS 由长期维护成本定。 |
| D4 | 会话标题生成 | 前端取首条消息兜底（零成本）vs 后端 LLM 摘要（需异步）。**先前端兜底，后端摘要作增强**。 |
| D5 | 工具返回完整展示 | 前端展开完整输出 vs 后端按 `risk_level` 脱敏/截断。涉及信息安全，需与 RBAC/审计一起定。 |
| D6 | 阶段命名统一 | 前端「固定阶段 + 动态任务」两级模型 vs 后端下发标准枚举。需与后端一起改（关联 9.4）。 |

## 四、落地顺序小结

1. **立即做 M1 + M2**（约 1 周）：SSE 生命周期 + 交互正确性 + 中文输入法修复。这是
   当前最痛、收益最直接、改动最集中的一批，每一条都直接决定用户「会不会被卡住」。
2. **随后 M3**（Markdown 基础设施），它是 M4/M5 复制、增量渲染、半成品兜底的前置。
3. **M4/M5/M6 并行**（阅读、状态、会话三线）。
4. **M7 → M8 → M9** 收尾（安全、视觉、技术债）。
