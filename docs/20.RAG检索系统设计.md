# GraphAgent RAG 检索系统设计

## 1. 概述

### 1.1 设计动机

GraphAgent 当前已具备基于 SQLite FTS5 的记忆检索系统（见 `19.记忆系统重构设计.md`），能够从历史对话中提取并检索用户偏好、架构决策、避坑经验等记忆。但该系统的检索范围局限于**对话中提取的结构化记忆**，无法检索外部文档（如项目文档、API 手册、技术规范、代码仓库等）中的知识。

引入 RAG（Retrieval-Augmented Generation）检索系统的核心动机：

1. **外部知识检索缺失**：Agent 在执行任务时无法检索项目文档、技术规范等外部知识源，导致需要用户反复提供上下文
2. **语义检索能力不足**：当前记忆系统仅支持 FTS5 关键词检索，缺乏向量语义检索能力，无法处理"含义相近但用词不同"的查询
3. **文档级别的知识管理**：缺少对项目文档、API 参考、设计文档等长文本的解析、分块、索引和检索能力

本设计结合 GraphAgent 的 Agent 编排特点，设计一套适配 GraphAgent 的轻量级 RAG 检索系统。

### 1.2 设计目标

| 目标 | 描述 |
|------|------|
| **文档知识库** | 支持创建多个知识库，每个知识库可导入多种格式的文档（Markdown、纯文本、代码文件、PDF） |
| **语义检索** | 引入向量嵌入（Embedding），支持基于语义相似度的文档片段检索 |
| **混合检索** | 结合关键词检索（FTS5）和向量检索，采用加权融合策略，提升检索召回率 |
| **Agent 工具化** | RAG 检索能力以标准工具形式暴露给 Agent，LLM 可自主决定何时检索、检索什么 |
| **统一检索入口** | 提供统一检索接口，同时覆盖记忆检索（已有）和文档检索（新增），Agent 无需区分数据来源 |
| **渐进式复杂度** | 支持从轻量级本地部署（ChromaDB + sentence-transformers）到大规模分布式（Milvus + API Embedding）的渐进升级 |
| **查询预处理** | 支持查询改写、查询分解、HyDE 等预处理策略，将 Agent 任务描述转化为更优的检索查询 |
| **多跳检索** | 支持迭代式检索（retrieve → reason → retrieve），处理需要跨文档推理的复杂问题 |
| **检索反馈闭环** | 记录检索结果的使用情况，通过隐式反馈持续优化检索权重和重排序策略 |
| **检索失败可恢复** | 导入流水线支持断点续跑，单次失败不影响已完成的工作，大文档导入可靠可控 |

### 3.1 核心数据结构

```python
# rag_types.py

from dataclasses import dataclass, field
from datetime import datetime
from enum import Enum
from typing import Optional


class ChunkStrategy(str, Enum):
    """分块策略枚举。"""
    TOKEN = "token"            # Token-based 固定大小分块
    RECURSIVE = "recursive"    # 递归分块（按自然分隔符）
    SEMANTIC = "semantic"      # 语义分块（基于嵌入相似度边界）


class ParserType(str, Enum):
    """文档解析器类型。"""
    AUTO = "auto"              # 自动检测
    MARKDOWN = "markdown"      # Markdown 文件
    TEXT = "text"              # 纯文本文件
    CODE = "code"              # 代码文件
    PDF = "pdf"                # PDF 文件（可选）


class EmbedderType(str, Enum):
    """嵌入器类型。"""
    OPENAI = "openai"          # OpenAI 兼容 API
    LOCAL = "local"            # 本地 sentence-transformers
    OLLAMA = "ollama"          # Ollama 嵌入模型
    ANTHROPIC = "anthropic"    # Anthropic 嵌入（Voyage 等）


class VectorStoreType(str, Enum):
    """向量库类型。"""
    CHROMADB = "chromadb"      # ChromaDB（默认，轻量级）
    MILVUS_LITE = "milvus_lite" # Milvus Lite（大规模场景）


class FusionMethod(str, Enum):
    """融合方法。"""
    WEIGHTED_SUM = "weighted_sum"  # 加权求和
    RRF = "rrf"                     # 倒数排名融合 (Reciprocal Rank Fusion)


class DocumentStatus(str, Enum):
    """文档状态枚举。

    状态转换规则：
    IMPORTING  → READY    (导入成功)
    IMPORTING  → ERROR    (导入失败或被取消)
    READY      → REIMPORTING (update_document 触发)
    REIMPORTING → READY   (重新导入成功)
    REIMPORTING → ERROR   (重新导入失败)
    READY/ERROR → DELETED (delete_document 触发)
    ERROR      → IMPORTING (resume_ingestion 触发续跑)
    """
    IMPORTING = "importing"        # 导入中（阶段 A 或 B 进行中）
    READY = "ready"                # 就绪（可被检索）
    ERROR = "error"                # 错误（导入失败，不可检索）
    REIMPORTING = "reimporting"    # 重新导入中
    DELETED = "deleted"            # 已删除（软删除，保留记录后清理）


@dataclass
class Document:
    """文档模型。"""
    id: str                              # 文档唯一 ID
    kb_name: str                         # 所属知识库名称
    filename: str                        # 原始文件名
    file_type: str                       # 文件类型（md, txt, py, pdf 等）
    parser_type: ParserType              # 使用的解析器
    content_hash: str                    # 原始内容 SHA256 哈希（去重用）
    status: DocumentStatus = DocumentStatus.IMPORTING  # 文档状态
    status_message: str = ""             # 状态附加信息（如错误原因）
    chunk_count: int = 0                 # 分块数量
    total_tokens: int = 0                # 总 token 数
    metadata: dict = field(default_factory=dict)  # 自定义元数据
    created_at: datetime = field(default_factory=datetime.now)
    updated_at: datetime = field(default_factory=datetime.now)


@dataclass
class Chunk:
    """文档分块模型。"""
    id: str                              # 分块唯一 ID
    doc_id: str                          # 所属文档 ID
    kb_name: str                         # 所属知识库名称
    content: str                         # 分块文本内容
    chunk_index: int                     # 在文档中的分块序号
    token_count: int                     # Token 数量
    embedding: Optional[list[float]] = None  # 向量嵌入
    metadata: dict = field(default_factory=dict)  # 元数据
    # metadata 包含:
    #   - source_file: 来源文件名
    #   - page_number: 页码（PDF）
    #   - heading_path: 标题路径（Markdown）
    #   - code_language: 代码语言（代码文件）
    #   - prev_chunk_id / next_chunk_id: 相邻分块 ID（上下文扩展用）


@dataclass
class KnowledgeBase:
    """知识库模型。"""
    name: str                            # 知识库名称（唯一标识）
    description: str = ""                # 描述
    embedder_type: EmbedderType = EmbedderType.OPENAI
    embedder_config: dict = field(default_factory=dict)  # 嵌入模型配置
    embedding_model: str = ""              # 实际使用的嵌入模型名称（如 text-embedding-3-small）
    embedding_dimension: int = 0           # 嵌入向量维度（如 1536），用于检测模型切换
    chunk_strategy: ChunkStrategy = ChunkStrategy.RECURSIVE
    chunk_size: int = 512                # 分块大小（tokens）
    chunk_overlap: int = 50              # 分块重叠（tokens）
    vector_store_type: VectorStoreType = VectorStoreType.CHROMADB
    fusion_method: FusionMethod = FusionMethod.WEIGHTED_SUM
    keyword_weight: float = 0.3          # 关键词检索权重（0-1）
    vector_weight: float = 0.7           # 向量检索权重（0-1）
    similarity_threshold: float = 0.5    # 相似度阈值
    document_count: int = 0              # 文档数量
    chunk_count: int = 0                 # 分块数量
    created_at: datetime = field(default_factory=datetime.now)
    updated_at: datetime = field(default_factory=datetime.now)


@dataclass
class SearchRequest:

    query: str                           # 查询文本
```

## 4. 文档导入流水线

### 4.1 流水线架构

文档导入流水线采用**两阶段设计**，将确定性操作（解析+分块）与网络依赖操作（嵌入+索引）分离，确保失败可恢复：

```
                        文档文件
                           │
                           ▼
┌──────────────────────────────────────────────────────────────┐
│  阶段 A: 文档准备 (确定性操作，可重试，零网络依赖)              │
│                                                              │
│  1. 文档解析 (Parser)                                        │
│     - 自动检测文件类型                                        │
│     - 提取文本内容和结构信息（标题、代码块、表格等）           │
│     - 生成 Document 对象                                      │
│                           │                                  │
│                           ▼                                  │
│  2. 分块 (Chunking)                                          │
│     - 按选择策略分割文本                                       │
│     - Token-based: 固定大小 + 重叠滑动窗口                     │
│     - Recursive: 优先按段落/标题分割，再按句子，最后按字符     │
│     - Semantic: 基于嵌入相似度检测语义边界（需独立轻量嵌入）    │
│     - 生成 Chunk 列表（持久化到暂存区）                        │
│                                                              │
│  阶段 A 完成后：Document + Chunks 已持久化到 DocumentStore     │
│  如果后续步骤失败，可从阶段 B 直接续跑                          │
└──────────────────────────┬───────────────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────────────┐
│  阶段 B: 向量化与索引 (可增量续跑，支持断点恢复)               │
│                                                              │
│  3. 嵌入生成 (Embedding)                                      │
│     - 批量调用嵌入模型（每 batch 持久化进度）                   │
│     - 嵌入缓存：相同内容的 chunk 复用已有向量                   │
│     - 速率限制 + 指数退避 + 重试队列                           │
│     - 每 batch 写入 checkpoint，失败可从最后一个 batch 续跑    │
│                           │                                  │
│                           ▼                                  │
│  4. 索引写入 (Indexing)                                       │
│     - FTS5 关键词索引：content + metadata                     │
│     - ChromaDB 向量索引：embedding + metadata                 │
│     - 更新知识库统计（文档数、分块数）                          │
│     - 阶段 B 全部完成后，标记文档为 ready                       │
└──────────────────────────────────────────────────────────────┘
```

**断点续跑机制**：每个 chunk 在 embedding 成功后立即写入 checkpoint 记录。如果 API 调用在 batch 中途失败，下次重试时跳过已有 checkpoint 的 chunk，从失败 batch 继续。阶段 A 的结果持久化在 `DocumentStore` 中，阶段 B 按 chunk 粒度续跑。

**索引一致性保证**：步骤 4 中 FTS5 和 ChromaDB 的写入在同一个数据库事务内完成（两者都用 SQLite 后端时），或按"先写 ChromaDB → 再写 FTS5 → 最后写 checkpoint"的顺序，确保 checkpoint 记录的 chunk 在两种索引中都已存在。系统启动时自动调用 `verify_index_integrity()` 检查一致性，发现不一致时记录警告日志并提供修复建议。

### 4.3 分块策略

#### 分块器基类

```python
# chunking/base_chunker.py

class BaseChunker(ABC):
    """分块器基类。

    所有分块器实现必须遵守 max_chunk_tokens 硬限制——
    单个 chunk 的 token 数不得超过嵌入模型的最大输入长度。
    """

    def __init__(self, chunk_size: int = 512, chunk_overlap: int = 50,
                 max_chunk_tokens: int = 8191):
        """初始化分块器。

        Args:
            chunk_size: 目标分块大小（tokens）。
            chunk_overlap: 相邻分块重叠量（tokens）。
            max_chunk_tokens: 硬限制——任何 chunk 的 token 数不得超过此值。
                              默认 8191（text-embedding-3-small 的上限）。
                              对于 BGE 系列模型，应设为 512。
                              MarkdownAwareChunker 的"代码块/表格不拆分"规则
                              在此硬限制下可能被强制打破（并记录 warning）。
        """
        self.chunk_size = chunk_size
        self.chunk_overlap = chunk_overlap
        self.max_chunk_tokens = max_chunk_tokens

    @abstractmethod
    def chunk(self, text: str, metadata: dict) -> list[Chunk]:
        ...

    def _validate_chunk_size(self, chunk: Chunk) -> bool:
        """校验单个 chunk 的 token 数是否在硬限制内。
        超限时记录 warning，由子类决定是否强制拆分。
        """
        if chunk.token_count > self.max_chunk_tokens:
            logger.warning(
                f"Chunk {chunk.id} token 数 ({chunk.token_count}) "
                f"超过 max_chunk_tokens ({self.max_chunk_tokens})，"
                f"可能超出嵌入模型输入上限"
            )
            return False
        return True
```

```python
# chunking/semantic_chunker.py

class SemanticChunker(BaseChunker):
    """语义分块器。

    基于嵌入相似度检测语义边界：
    1. 将文本按句子分割
    2. 计算相邻句子的嵌入相似度
    3. 在相似度骤降的位置（语义边界）切分
    4. 合并句子直到达到 chunk_size

    这比固定大小分块更能保留语义完整性，但计算成本更高。

    **重要设计决策：避免循环依赖**

    语义分块器需要嵌入能力来检测语义边界，但嵌入服务位于流水线后续阶段。
    为避免循环依赖，语义分块器使用独立的轻量嵌入模型，
    与知识库的主嵌入模型（用于检索）解耦：
    - 默认使用 all-MiniLM-L6-v2（384维, ~80MB），本地运行
    - 仅用于边界检测，不参与后续检索
    - 在分块阶段完成句子嵌入后即可释放模型

    权衡：相比主嵌入模型（如 text-embedding-3-small），轻量模型的边界检测
    精度稍低，但其优势在于：(1) 无网络依赖 (2) 零成本 (3) 速度快。
    """

    def __init__(self, boundary_model: str = "all-MiniLM-L6-v2",
                 similarity_percentile_threshold: int = 90):
        from sentence_transformers import SentenceTransformer
        self.boundary_model = SentenceTransformer(boundary_model)

    def chunk(self, text: str, metadata: dict) -> list[Chunk]:
```

```python
# vector_store/base_vector_store.py

class BaseVectorStore(ABC):
    """向量库抽象接口。

    设计原则：
    - 统一接口，屏蔽不同后端的实现差异
    - 支持通过配置切换后端
    """

    @abstractmethod
    async def create_collection(self, kb_name: str, dimension: int) -> None:
        """创建知识库对应的向量集合。"""
        ...

    @abstractmethod
    async def add_chunks(self, kb_name: str, chunks: list[Chunk]) -> None:
        """批量添加分块向量。

        接收完整 Chunk 对象以获取 id、embedding、metadata，
        但存储层不持有 Chunk 的业务逻辑引用。
        """
        ...

    @abstractmethod
    async def search(
        self,
        kb_name: str,
        query_vector: list[float],
        top_k: int = 10,
        filter: dict | None = None,
    ) -> list[tuple[str, float, dict]]:
        """向量相似度检索。

        Returns:
            (chunk_id, similarity_score, metadata) 列表，按相似度降序

        设计决策：返回 (chunk_id, score, metadata) 而非完整 Chunk 对象。

        ...

        """删除知识库的向量集合。"""
        ...

    @abstractmethod

        """获取集合统计信息：chunk_count, dimension 等。"""

    @abstractmethod
```

```python
        - 输入："GraphAgent 的上下文管理机制和记忆系统如何交互"
        - 输出：[
            "GraphAgent 上下文管理 架构",
            "记忆系统 记忆提取 存储 检索",
            "上下文注入 记忆注入 Agent 编排"
          ]

        适用于需要跨文档推理的复杂问题。

    async def hyde(self, query: str) -> list[float]:
        """HyDE (Hypothetical Document Embeddings)：
        1. LLM 生成一个假设的答案文档
        2. 用假设答案的嵌入向量进行检索

        这通常比直接用问题的嵌入向量检索更有效，

        # 假设答案是一段模拟文档文本，应与文档使用相同编码
        embeddings = self.embedder.embed([hypothetical_answer])
        return embeddings[0]
```

### 6.7 多跳检索

复杂问题往往需要跨文档推理（"为什么 Guard 层采用 FTS5 而非向量检索？"——需要先检索 Guard 层职责，再检索检索策略选型理由）。单次检索无法满足这类需求。

**LLM 调用成本说明**：多跳检索每跳涉及 2 次额外 LLM 调用：

| 调用 | 用途 | 每跳次数 |
|------|------|---------|
| `_evaluate_sufficiency` | 评估当前检索结果是否足够回答原始问题 | 1 |
| `_generate_next_query` | 基于已有信息生成下一跳检索查询 | 1 |

3 跳完整流程的 LLM 调用总量：

| 环节 | LLM 调用数 |
|------|-----------|
| 查询预处理（如启用改写） | 1 |
| 第 1 跳：初始检索 | 0（仅 embedding + 向量检索） |
| 第 1 跳后：充分性评估 | 1 |
| 第 2 跳：检索 | 0 |
| 第 2 跳后：充分性评估 + 查询生成 | 2 |
| 第 3 跳：检索 | 0 |
| 第 3 跳后：充分性评估（终判） | 1 |
| **合计** | **5 次 LLM 调用**（含预处理则为 6 次） |

> 因此 `enable_multi_hop` 默认关闭。仅在 Agent 判断问题确实需要跨文档推理时才开启，避免简单查询产生不必要的 LLM 调用开销。

```python

    """

    def __init__(self, rag_retriever: RAGRetriever, llm: Any):
        self.rag_retriever = rag_retriever
        self.llm = llm

    async def retrieve(
        self,
        query: str,
        max_hops: int = 3,
        top_k_per_hop: int = 5,
        early_stop_threshold: float = 0.9,

        """执行多跳检索。

        流程：
        1. 第 1 跳：用原始查询检索
        2. LLM 评估检索结果的信息充分性（0-1 分）
        3. 如果分数 < early_stop_threshold 且 hop < max_hops：
           - LLM 基于已知信息生成下一跳的检索查询
           - 执行下一跳检索
           - 合并去重历史结果
        4. 达到充分性或最大跳数后返回
        """
        ...

    async def _generate_next_query(
        self,
        original_query: str,
        accumulated_chunks: list[Chunk],
    ) -> str:
        """基于已有信息生成下一跳的检索查询。

        Prompt 模板：
        '''
        原始问题: {original_query}

        已检索到的信息:
        {accumulated_content}

        为了完整回答原始问题，还需要了解什么信息？
        请生成一个简短的检索查询来补充缺失的信息。
        检索查询:
        '''
        """
        ...

    async def _evaluate_sufficiency(
        self, query: str, chunks: list[Chunk]
    ) -> float:
        """LLM 评估当前检索结果是否足够回答原始问题。"""
        ...


@dataclass
class MultiHopResult:
    """多跳检索结果。"""
    final_chunks: list[SearchResult]     # 合并去重后的最终结果
    hops: list[HopResult]                # 每跳的详细信息
    total_hops: int                      # 实际执行跳数
    sufficiency_score: float             # 最终充分性评分


@dataclass
class HopResult:
    """单跳检索结果。"""
    hop_index: int                       # 跳数序号（从 1 开始）
    query: str                           # 本轮使用的查询
    results: list[SearchResult]          # 本轮检索结果
    new_information: list[str]           # 本轮新增的信息（chunk_id 列表）
```

### 6.10 检索结果缓存

在一个 Agent 会话中，同一查询可能被多次执行（追问、重试等场景）。为避免重复的 embedding API 调用和检索计算，提供会话级检索结果缓存：

```python
# retrieval/retrieval_cache.py

class RetrievalCache:
    """检索结果缓存（会话级 LRU）。

    缓存 key: (query_hash, kb_names_hash, top_k, metadata_filter_hash)
    缓存 value: list[SearchResult]

    仅缓存单跳检索（非 multi-hop）结果，因为多跳检索涉及 LLM 推理，
    每次执行结果可能不同。
    """

    def __init__(self, max_size: int = 100, ttl_seconds: int = 300):
        """初始化缓存。

        Args:
            max_size: 最大缓存条目数，默认 100。
            ttl_seconds: 缓存有效期（秒），默认 300（5 分钟）。
                        超过 TTL 后缓存失效，需重新检索。
                        设为 5 分钟与 Anthropic prompt cache TTL 对齐。
        """
        self._cache: dict[str, tuple[float, list[SearchResult]]] = {}
        self.max_size = max_size
        self.ttl = ttl_seconds

    def _make_key(self, query: str, kb_names: list[str],
                  top_k: int, metadata_filter: dict | None) -> str:
        """生成缓存 key。使用 SHA256 哈希缩短 key 长度。"""
        ...

    def get(self, query: str, kb_names: list[str],
            top_k: int, metadata_filter: dict | None = None) -> list[SearchResult] | None:
        """查询缓存，命中则返回结果，过期或未命中返回 None。"""
        ...

    def put(self, query: str, kb_names: list[str],
            top_k: int, results: list[SearchResult],
            metadata_filter: dict | None = None) -> None:
        """写入缓存。超过 max_size 时淘汰最旧的条目（LRU）。"""
        ...

    def invalidate(self, kb_name: str | None = None) -> None:
        """失效缓存。

        - kb_name=None: 清空全部缓存
        - kb_name="xxx": 仅清空涉及该知识库的缓存条目
        （在文档导入/删除后调用，确保缓存不返回过期数据）
        """
        ...
```

**缓存失效策略**：当 `ingest_documents`、`ingest_text`、`delete_documents`、`reindex_knowledge_base` 操作成功后，自动调用 `invalidate(kb_name)` 失效涉及知识库的缓存。

### 6.11 向量库降级策略

当 ChromaDB 文件损坏或向量检索不可用时，系统应能自动降级为纯关键词检索：

```python
# retrieval/rag_retriever.py (补充)

class RAGRetriever:
    async def retrieve(self, request: SearchRequest) -> list[SearchResult]:
        try:
            vector_results = await self.vector_searcher.search(...)
        except VectorStoreUnavailableError as e:
            logger.warning(f"向量检索不可用，降级为纯关键词检索: {e}")
            vector_results = []  # 降级：无向量结果
            self._degraded_mode = True

        keyword_results = self.keyword_searcher.search(...)

        if vector_results:
            results = self.fusion_engine.fuse(keyword_results, vector_results, ...)
        else:
            # 降级模式：仅使用关键词结果
            results = [(chunk, score) for chunk, score in keyword_results[:request.top_k]]

        ...

    @property
    def is_degraded(self) -> bool:
        """当前是否处于降级模式（仅关键词检索）。"""
        return self._degraded_mode
```

**降级触发条件**：
- ChromaDB collection 查询抛出异常
- 向量维度不匹配（但未执行 reindex）
- ChromaDB SQLite 文件损坏（database disk image is malformed）

**降级行为**：
- 检索结果中 `vector_score` 全部为 0，`source` 标注为 `keyword_only`
- 日志记录 WARNING 级别信息
- 不影响 ingest 操作（可继续导入文档，但只写 FTS5 索引）
- 下次启动时自动尝试恢复向量检索

**恢复方式**：
- 修复 ChromaDB 后重启服务即可自动恢复
- 如需重建向量索引，使用 `reindex_knowledge_base` 工具

```python
@tool(
    name="reindex_knowledge_base",
    description="重建知识库的向量索引。在切换嵌入模型后必须执行此操作，否则维度不匹配将导致检索失败。"

async def reindex_knowledge_base(
    kb_name: str,
    new_embedder_type: str | None = None,
    new_embedder_model: str | None = None,
    cancellation_token: CancellationToken | None = None,
) -> dict:
    """重建知识库索引。

    采用"影子重建"策略，确保失败时不丢失数据：

    流程：
    1. 检查当前嵌入模型与目标嵌入模型的维度是否一致
    2. 如果一致：无需 reindex，直接返回
    3. 如果不一致：
       a. 创建临时向量集合 "{kb_name}_reindex_tmp"
       b. 遍历所有 chunk，用新嵌入模型生成向量 → 写入临时集合
          （每 batch 检查 cancellation_token，响应取消请求）
       c. 每 batch 写入 checkpoint（复用 IngestionPipeline 的 checkpoint 机制）
       d. 全部完成后验证临时集合的 chunk 数量与原集合一致
       e. 原子替换：删除旧集合，将临时集合重命名为正式名称
       f. 更新知识库的 embedding_model 和 embedding_dimension
       g. 清理 checkpoint 和临时文件

    - 步骤 b 期间收到取消：停止处理，清理临时集合，保留旧集合完好
    - 返回 {"status": "cancelled", "chunks_reindexed": N, "chunks_remaining": M}

    失败恢复：
    - 步骤 a-c 期间失败：旧集合完好，可 retry；临时集合在下次 reindex 时自动清理
    - 步骤 d 验证失败：保留旧集合，报告不一致让用户介入
    - 步骤 e 期间失败：两个集合都存在，下次启动时自动选择 chunk 数量多的那个

    Args:
        kb_name: 目标知识库名称。
        new_embedder_type: 新的嵌入器类型（不指定则使用当前配置）。
        new_embedder_model: 新的嵌入模型名称。
```

## 8. 统一检索层

### 8.1 设计原则

统一检索层的核心思想是：**Agent 不需要知道信息来自记忆还是文档，只需描述信息需求，系统自动从最合适的数据源检索。**

```python
# unified_retriever.py

class UnifiedRetriever:
    """统一检索器。

    支持多种检索模式：
    - 标准检索（memory + document 关键词+向量）
    - 扩展检索（未来可接入 GraphRAG 知识图谱检索）

    侧重于跨多个数据源的联合检索。
    """

    def __init__(self, memory_searcher: MemorySearcher,
                 rag_retriever: RAGRetriever,
                 llm: Any):
        self.memory_searcher = memory_searcher
        self.rag_retriever = rag_retriever
        self.llm = llm

    async def search(self, query: str,
                     sources: list[str] | None = None,
                     memory_search_params: dict | None = None,
                     document_search_params: dict | None = None,
                     merge: bool = True) -> UnifiedSearchResponse:
        """统一检索。

        检索策略：
        1. Parallel（默认）: 并行检索两种数据源，通过 RRF 合并结果。
           适用于大多数场景，延迟最低。

        2. Cascaded: 先在 memory 中检索，如果 top 结果的平均 score
           低于阈值（默认 0.4），则继续检索 documents。
           适用于 memory 覆盖率高、documents 作为补充的场景。
           优势：大多数情况下只需一次检索，节省 token。

        3. Selective: LLM 分析查询后返回数据源选择建议。
           适用于 Agent 明确知道信息来源的场景。
           例如：查询"用户偏好用哪个配色" → 只需 memory；
                 查询"部署文档中 Docker 的配置" → 只需 documents。
           策略选择逻辑（由 LLM 完成）：
           - 查询涉及个人偏好/历史决策 → memory
           - 查询涉及技术规范/API/代码 → documents
           - 查询涉及两者 → parallel
        """

    async def _cascaded_search(self, query: str, ...) -> UnifiedSearchResponse:
        """级联检索：先 memory，不足时自动补充 documents。

        充分性判断：如果 memory top-3 的平均 score > cascaded_threshold，
        认为 memory 结果已充分，跳过 documents 检索。
        cascaded_threshold 默认为 0.4（memory FTS5 score 归一化后）。
        """
        ...

    async def _selective_search(self, query: str, ...) -> UnifiedSearchResponse:
        """选择性检索：LLM 决定检索哪些数据源。

        使用轻量级 prompt 让 LLM 判断查询的预期信息来源。
        避免为简单查询同时检索两个数据源。
        """
        ...
        ...

    def _merge_results(self, memory_results: list,
                       document_results: list) -> UnifiedSearchResponse:
        """合并和去重不同来源的结果。

        **关键设计决策：跨源分数不可直接比较**

        Memory 检索返回 BM25 原始分（值域无上限，通常 0~50+），
        Document 检索返回 min-max 归一化后的融合分数（值域 [0, 1]）。
        直接按 score 比较会导致一种来源的结果系统性压制另一种。

        解决方案：统一使用 RRF（倒数排名融合）进行跨源合并：
        - 各来源内部按原始分数排名
        - RRF score = 1/(k + rank_memory) + 1/(k + rank_document)，其中 k=60
        - 按 RRF 分数降序排列
        - 标记每条结果的来源（memory / document）
        - 可选：LLM 生成合并摘要
        """
        ...

    async def _generate_summary(self, query: str,
                                results: list[SearchResult]) -> str:
        """使用 LLM 生成检索结果的综合摘要。

        - 标注引用来源（文档名、分块 ID）
        - 整合多源信息
        """
        ...
```

### 8.3 上下文预算控制

| 检索来源 | 默认 top_k | 单条最大 tokens | 最大预算 |
|---------|-----------|----------------|---------|
| 记忆检索 (memory) | 3 | 300 | ~900 tokens |
| 文档检索 (documents) | 5 | 500 | ~2500 tokens |
| LLM 摘要 (summary) | — | — | ~300 tokens |
| **合计** | | | **~3700 tokens** |

**配置迁移策略**：

当 RAG 系统升级导致 kb_config.yaml 结构变更时，通过 `schema_version` 字段识别版本并执行迁移：

```python
# document_store.py — KnowledgeBaseManager

class KnowledgeBaseManager:
    CURRENT_SCHEMA_VERSION = 1

    def _migrate_config(self, kb_name: str, config: dict) -> dict:
        """根据 schema_version 执行配置迁移。

        迁移链：
        version 0 → 1: 初始版本（当前），无需迁移
        version 1 → 2: (未来) 根据实际变更定义
        """
        version = config.get("schema_version", 0)
        while version < self.CURRENT_SCHEMA_VERSION:
            migrator = self._MIGRATIONS.get(version)
            if migrator:
                config = migrator(config)
            version += 1
        config["schema_version"] = self.CURRENT_SCHEMA_VERSION
        return config
```

### 11.3 初始化流程

```python
# context_utils.py 新增

_rag_service: RAGService | None = None

def get_rag_service() -> RAGService | None:
    """获取 RAG 服务实例（懒加载）。

    仅在 session_config.yaml 中 rag.enabled=true 时初始化。
    初始化时自动检测嵌入模型维度与已有知识库的兼容性。
    """
    global _rag_service
    if _rag_service is None:
        config = load_session_config()
        if config.get("rag", {}).get("enabled", False):
            _rag_service = RAGService.initialize(config["rag"])
            # 启动时检测 kb_registry.json 完整性
            if not _rag_service.is_registry_healthy():
                logger.warning(
                    "kb_registry.json 损坏或缺失，正在从磁盘扫描重建..."
                )
                recovered = _rag_service.rebuild_registry_from_disk()
                logger.info(
                    f"已从磁盘重建 kb_registry.json，恢复 {len(recovered)} 个知识库"
                )
            # 启动时检测维度不匹配
            mismatched = _rag_service.check_embedding_dimension_mismatch()
            if mismatched:
                logger.warning(
                    f"检测到 {len(mismatched)} 个知识库的嵌入维度与当前模型不匹配。"
                    f"请使用 reindex_knowledge_base 工具重建索引。"
                    f"不匹配的知识库: {[m['kb_name'] for m in mismatched]}"
                )
            # 启动时检测和清理残留的临时 reindex 集合
            _rag_service.cleanup_orphaned_reindex_collections()
    return _rag_service
```

## 14. 安全考量

### 14.1 数据安全

| 考量 | 设计决策 |
|------|---------|
| **文档访问控制** | 知识库按项目隔离，不同项目无法互相检索 |
| **嵌入数据隐私** | 本地嵌入模型（sentence-transformers）确保文档内容不出本地 |
| **文件路径安全** | 导入文件路径验证，防止路径遍历攻击 |
| **内容过滤** | 可选的内容安全过滤，防止敏感信息被检索和注入上下文 |
| **嵌入缓存安全** | 嵌入缓存按 content_hash 索引，不存储原始文本 |
| **Prompt Injection 防御** | LLM 重排序器中注入的 chunk 内容需做 sanitize：包裹在 markdown fence 中，添加显式的"以下为待评估文档片段"标记，避免恶意文档内容操控 LLM 判断 |

### 14.2 并发安全

| 考量 | 设计决策 |
|------|---------|
| **写入串行化** | SQLite FTS5 和 ChromaDB（底层 SQLite）均不支持多写入者并发。所有写入操作（ingest、delete、reindex）通过单个 `asyncio.Lock` 串行化，同一知识库同一时间只有一个写入者 |
| **读写并发** | ChromaDB 和 SQLite 支持写时读（WAL 模式），读取操作（search、get_document）无需获取写锁 |
| **跨知识库并发** | 不同知识库的写入操作可并行执行（使用 `kb_name` 粒度的锁） |
| **Agent 多实例安全** | 由于 SQLite 文件级锁的限制，多进程同时写入同一知识库可能失败。建议在生产环境中使用 Milvus Lite 后端（支持更好的并发），或确保 RAG 服务以单进程模式运行 |

### 14.3 资源安全

| 考量 | 设计决策 |
|------|---------|
| **文档大小限制** | 单个文档最大 10MB（可配置） |
| **知识库大小限制** | 每个知识库最多 10000 个分块（可配置） |
| **API 速率限制** | 嵌入 API 调用速率限制（指数退避重试最多 3 次），避免触发 LLM 提供商限流 |
| **检索超时** | 检索操作超时时间 30 秒 |
| **上下文注入限制** | 检索结果注入上下文有 token 预算上限 |

## 15. 附录

### 15.1 关键决策理由

| 决策 | 选择 | 理由 |
|------|------|------|
| 向量库默认后端 | ChromaDB | 嵌入式运行、零配置、与 GraphAgent 轻量 Agent 定位匹配 |
| 默认融合权重 | 关键词 0.3 : 向量 0.7 | Agent 查询通常是自然语言（语义为主），但精确匹配（API 名称、配置键等）需要关键词补充 |
| 默认分块策略 | Recursive（递归） | 在保留语义结构和实现简单性之间取平衡，优于 Token-based 固定切分 |
| 默认嵌入模型 | OpenAI text-embedding-3-small | 复用现有 LLM API 配置，无需额外部署 |
| 重排序方式 | LLM-based（默认） | 复用现有 LLM，无需加载额外模型 |
| 语义分块嵌入模型 | 独立轻量模型（all-MiniLM-L6-v2） | 语义分块发生在流水线早期阶段，不能依赖主嵌入服务（循环依赖）；独立轻量模型同时保证零网络依赖和高速度 |
| 向量存储返回类型 | `(chunk_id, score, metadata)` 而非 `(Chunk, float)` | 存储层不应耦合业务数据模型；上层通过 chunk_id 从 DocumentStore 重建 Chunk |
| 导入流水线设计 | 两阶段 + chunk 级 checkpoint | 解析/分块是确定性操作，嵌入是网络依赖操作。分离后可实现断点续跑，大文档导入不掉链 |
| 查询预处理 | 默认启用查询改写 | Agent 的任务描述往往口语化，不适合直接作为检索 query；查询改写提升召回率 |
| 多跳检索 | 可选（默认关闭） | 仅复杂跨文档推理问题需要；默认关闭以节省 token 和延迟 |
| 嵌入模型迁移 | 提供 reindex 工具 + 启动时维度检测 | 切换嵌入模型后旧向量与新查询维度不匹配，必须重建索引；启动时主动检测避免静默失败 |
| 冷启动 | 自动扫描 docs/ 目录并导入 | 让 RAG 系统开箱即用，降低使用门槛 |
| 写入并发 | asyncio.Lock 串行化（kb_name 粒度） | SQLite 不支持多写入者；不同知识库可并行写入 |
| 与记忆系统的关系 | 并列 + 统一检索层 | 保持模块独立性，通过 UnifiedRetriever 提供一站式检索 |
| 文档解析器范围 | MD/TXT/代码（Phase 1-2）+ PDF（Phase 6） | Agent 主要处理文本和代码，PDF 是低频需求 |
| 跨源分数合并 | RRF（倒数排名融合） | Memory 的 BM25 分数与 Document 的融合分数值域不同，不可直接比较；RRF 仅依赖排名，天然跨源可比 |
| 索引一致性保证 | 阶段 B 写入顺序 + 启动时 verify_index_integrity | ChromaDB 和 FTS5 需同步写入，异常崩溃后自动检测和修复 |
| 元数据过滤 | 支持（通过 metadata_filter 参数） | Chunk 携带丰富的元数据（语言、文件名、标题路径等），过滤能力让 Agent 精确检索 |
| get_document 截断 | 默认 max_tokens=8000，智能截断 | 10MB 文档 ≈ 250 万 tokens，远超上下文窗口，必须截断保护 |
| 检索缓存 | 会话级 LRU（100 条 / 5 分钟 TTL） | 同一会话中重复查询避免重复的 embedding API 调用和检索计算 |
| ChromaDB 降级 | 自动 fallback 为纯关键词检索 | ChromaDB 损坏时不应整个 RAG 不可用；降级后仍可检索，恢复后自动还原 |
| ingest_text 文件名 | title + 时间戳后缀 | 避免 Agent 使用相同 title 时的文件名冲突 |
| preview_chunking 统计 | 增加 min/max/std/分布 | 调参需要分布信息，仅看平均值和预览内容不够 |
| reindex 策略 | 影子重建（新建临时集合 → 验证 → 原子替换） | 先删后建在失败时导致向量索引完全丢失；影子重建在任何失败阶段都保留旧集合 |
| kb_registry 恢复 | 启动时扫描 data/rag/ 目录重建 | 单 JSON 文件损坏导致所有 KB 不可见；磁盘扫描保证数据不丢 |
| 文档状态生命周期 | DocumentStatus 枚举 + 状态机 | 检索/验证/续跑等操作需要明确知道文档当前状态以做出正确决策 |
| preview_chunking 语义分块 | 降级为递归分块近似预览 | 语义分块需加载模型并计算嵌入（~80MB, 10-30s），对预览过于昂贵 |
| get_document 模糊匹配 | 精确子串匹配（case-insensitive），多匹配返回最近更新 | 确定性语义避免 Agent 混淆 |
| kb_config 版本控制 | schema_version 字段 + 迁移链 | 配置结构变更时旧配置文件无法解析，需要版本识别和迁移 |
| list_documents 工具 | 支持分页 + 状态过滤 | 填补 KB 级和文档级之间的粒度断层，Agent 可浏览 KB 内容 |
| unified_search 参数对称 | 增加 include_adjacent 和 filter | 与 search_documents 保持能力一致，不因入口不同而丢失功能 |
| 分块硬限制 | BaseChunker.max_chunk_tokens（默认 8191） | 代码块/表格不拆分规则可能产生超大 chunk，需校验嵌入模型上限 |
| Markdown frontmatter | 自动检测并提取 YAML frontmatter | 导入 GraphAgent 记忆文件时避免将元数据头当作正文检索 |
| 多跳检索成本 | 文档化：3 跳最多 5 次 LLM 调用 | 让开发者有合理预期，默认关闭以节省成本 |
| HyDE 嵌入方法 | 使用 embed() 而非 embed_query() | 假设答案本质是模拟文档，BGE 等模型的 query/doc 编码不同 |
| 检索反馈双通道 | 隐式检测 + 显式上报（report_search_quality） | 隐式检测有误差，Agent 主动标记更可靠 |
| reindex 取消 | 支持 cancellation_token | 与 ingest 保持操作一致性，reindex 同样可能耗时很长 |
| ingest 目录导入 | recursive 参数支持目录递归扫描 | 减少 Agent 手动枚举文件的负担 |

### 15.2 与记忆系统检索的对比

| 维度 | 记忆系统 (FTS5) | RAG 文档检索 |
|------|----------------|-------------|
| **数据来源** | 对话中 LLM 提取的记忆 | 用户导入的文档文件 |
| **数据特点** | 结构化（type/scope/status）+ 短文本（~200 tokens/条） | 非结构化长文本，被分割为 chunk |
| **检索方式** | FTS5 关键词全文检索 | 关键词（FTS5）+ 向量（ChromaDB）混合检索 |
| **重排序** | scope 优先级 + FTS5 rank | 融合分数 + LLM 重排序 |
| **工具名称** | `search_memory` | `search_documents` |
| **LLM 自主决定** | 是（通过 tool calling） | 是（通过 tool calling） |
| **上下文注入** | Layer 2 (Guard) + Layer 3 (Plan) | SubAgent 按需调用 |
| **状态管理** | ACTIVE / ARCHIVED / INVALID | 无（文档版本管理即状态管理） |
