# GraphAgent 记忆系统重构设计

## 1. 概述

### 1.1 重构动机

现有记忆系统（见 `18.记忆系统设计.md`）采用**双层记忆模型**（用户画像 + 主题记忆），以 Markdown + JSON 索引文件的方式存储，检索依赖**关键词匹配 + 时间衰减**排序。经过实践发现以下不足：

1. **记忆粒度粗**：以"主题"为组织单元，同一主题下多条经验耦合在一个文件中，不利于单条记忆的独立检索和生命周期管理
2. **检索效率低**：遍历 `index.json` + 逐个加载 Markdown 文件，无全文索引，关键词匹配精度有限
3. **状态管理缺失**：记忆没有明确的状态标记（活跃/归档/废弃），过期处理简单粗暴
4. **工具化程度低**：记忆检索未暴露为 Agent 可调用的标准工具，LLM 无法自主决定何时检索、如何检索
5. **无访问追踪**：缺少访问频率和使用时间的记录，无法基于实际使用情况优化记忆留存策略

### 1.2 重构目标

| 目标 | 描述 |
|------|------|
| **细粒度记忆** | 每条记忆拥有唯一 ID 和完整元数据，按创建日期合并存储（一天一个 Markdown 文件），控制文件数量 |
| **全文检索** | 引入 SQLite FTS5 建立全文索引，支持高效、准确的记忆检索 |
| **明确状态机** | 记忆具备 ACTIVE → ARCHIVED → INVALID 的完整生命周期 |
| **工具化检索** | 新增 `search_memory` 工具，由 LLM 自主决定检索参数并发起检索 |
| **访问追踪** | 记录每次检索使用，支撑后续智能淘汰策略 |

## 2. 记忆数据模型

### 2.1 核心字段

每条记忆包含以下字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | ✅ | 唯一标识，格式 `{日期}_{时间}_{6位随机码}`，如 `2026-06-04_20-29_asdfgh` |
| `type` | enum | ✅ | 记忆类型，见 §2.2 |
| `scope` | enum | ✅ | 作用范围，见 §2.3 |
| `status` | enum | ✅ | 生命周期状态，见 §2.4 |
| `tags` | list[str] | ✅ | 检索关键字，每条记忆 1~3 个 |
| `session_id` | string \| None | ❌ | 关联的会话 ID，仅 `scope=session` 时有值，用于批量归档时精准定位 |
| `created_at` | datetime | ✅ | 创建时间（ISO 8601） |
| `updated_at` | datetime | ✅ | 最后更新时间（ISO 8601） |
| `access_at` | datetime | ✅ | 最后一次被检索引用的时间 |
| `access_count` | int | ✅ | 被检索引用的累计次数 |
| `content` | string | ✅ | 记忆的具体内容（Markdown 格式） |

### 2.2 记忆类型（type）

| 取值 | 含义 | 示例 |
|------|------|------|
| `user_preference` | 用户偏好：交互风格、语言、格式偏好 | "用户希望所有回复使用简体中文" |
| `arch_design` | 架构设计记忆：技术选型、分层架构、模块划分、部署方案 | "本项目采用三层编排架构：Guard → Plan → Execute" |
| `project_rule` | 项目规范：编码规约、命名规则、项目约束、流程制度 | "Python 文件使用 4 空格缩进，禁止 tab" |
| `design_pattern` | 编码建模：领域模型、接口定义、设计模式、组件封装 | "Agent 模块统一使用抽象基类定义接口" |
| `bug_pitfall` | Bug 踩坑档案：历史故障、报错诱因、修复方案、避坑经验 | "Windows 下 asyncio.create_task 会导致 RuntimeError" |
| `general_knowledge` | 通用技术常识：编程语言特性、第三方 SDK 用法、通用算法 | "Python 3.10+ 支持 match-case 模式匹配" |

> **扩展性**：`type` 取值随 GraphAgent 功能扩展可持续增加，例如后续可增加 `tool_usage`（工具使用经验）、`error_handling`（异常处理模式）等。

### 2.3 作用范围（scope）

| 取值 | 含义 | 生命周期 |
|------|------|---------|
| `user` | 用户级记忆 | 跨项目、跨会话，跟随用户长期有效 |
| `project` | 项目级记忆 | 仅在当前项目内有效，换项目不可见 |
| `session` | 会话级记忆 | 仅在当前会话内有效，会话结束后自动归档 |

**检索优先级**：`session` > `project` > `user`（范围越小、越贴近当前上下文的记忆优先返回）。

### 2.4 记忆状态（status）与生命周期

```
         创建 ──→ ┌──────────┐ ←── 更新 + 唤醒（被检索命中）
                 │  ACTIVE  │
                 └────┬─────┘
                      │
         时效过期 ────┼──── 长期未用 ──── 用户手动归档
         会话结束     │                 归档指令
                      ▼
                 ┌──────────┐
                 │ ARCHIVED │
                 └────┬─────┘
                      │
         内容被新记忆 ─┼─ 内容错误/过时作废
         完全覆盖      │
                      ▼
                 ┌──────────┐
                 │ INVALID  │
                 └──────────┘
```

| 状态 | 含义 | 检索行为 |
|------|------|---------|
| `ACTIVE` | 活跃可用态，内容真实有效 | 参与 FTS5 检索 |
| `ARCHIVED` | 归档休眠态，内容真实但时效性过期或长期极少使用 | 默认不参与检索，可通过 `include_archived=true` 显式检索 |
| `INVALID` | 废弃失效态，内容错误或已被新记忆完全覆盖 | 永久禁用检索，仅保留文件备查 |

**状态流转规则**：

1. **ACTIVE → ARCHIVED**：
   - `access_count` 很低（如 30 天内访问 < 2 次）且 `updated_at` 距今超过 90 天
   - 会话结束时 `session` 范围的记忆自动归档
   - 用户手动归档

2. **ARCHIVED → ACTIVE**：
   - 被检索命中时自动激活（"唤醒"机制）

3. **ACTIVE/ARCHIVED → INVALID**：
   - 用户明确标记为错误
   - 新记忆完全覆盖旧记忆内容时，旧记忆标记为 INVALID
   - 内容过期作废（如某个 API 在新版本中已移除）

## 3. 存储设计

### 3.1 磁盘目录结构

```
data/memory/
├── user/                              # User 范围的记忆（按创建日期分文件）
│   ├── 2026-06-03.md                  # 6月3日创建的所有 user 记忆
│   ├── 2026-06-04.md                  # 6月4日创建的所有 user 记忆
│   └── ...
├── project/                           # Project 范围的记忆（按创建日期分文件）
│   ├── 2026-05-28.md
│   ├── 2026-06-04.md
│   └── ...
├── session/                           # Session 范围的记忆（按创建日期分文件）
│   ├── 2026-06-04.md
│   └── ...
├── archive/                           # ARCHIVED 状态的记忆（按归档日期分文件）
│   ├── 2026-06-10.md                  # 6月10日归档的所有记忆
│   └── ...
└── memory.db                          # SQLite 数据库（含 FTS5 索引）
```

> **设计原则**：
> - 文件按 `scope` 分目录存放，**每天每 scope 最多一个 Markdown 文件**（如 `user/2026-06-04.md`），当天产生的该 scope 的记忆全部追加到此文件中
> - `archive/` 目录存放 ARCHIVED 状态的记忆，按**归档日期**分文件
> - INVALID 状态的记忆保留在原文件内不移动，仅在 DB 中标记状态为不可检索
> - 文件名格式为 `{date}.md`，颗粒度为天，可读性强且有效控制文件数量
>
> **文件数量估算**：假设每天 3 个 scope（user/project/session）各产生一个文件，一年最多 `3 × 365 = 1095` 个文件，加上 `archive/` 约同样数量，总计约 2000+ 个文件。相比每条记忆一个文件的方案（若每天产生 10 条记忆则一年 10950 个文件），文件数量减少约一个数量级。

### 3.2 Markdown 文件格式

**一个 Markdown 文件存储当天同一 scope 下产生的所有记忆**。文件命名为 `{date}.md`（如 `2026-06-04.md`），采用**文件级 YAML frontmatter + 多条记忆记录**的格式。每条记忆以 H2 标题分隔，标题即为记忆 ID，正文为 YAML 格式的元数据键值对 + 记忆内容。

**文件示例**（`user/2026-06-04.md`，当天创建了 2 条 user 范围的记忆）：

```markdown
---
date: "2026-06-04"
scope: "user"
memory_count: 2
---

# 2026-06-04 记忆记录 (user)

## 2026-06-04_20-29_asdfgh
- **type**: user_preference
- **status**: ACTIVE
- **tags**:
  - 中文回复
  - 代码风格
  - Markdown
- **created_at**: "2026-06-04T20:29:00+08:00"
- **updated_at**: "2026-06-04T20:35:00+08:00"
- **access_at**: "2026-06-04T20:35:00+08:00"
- **access_count**: 3

    用户希望所有回复使用简体中文。代码注释使用英文，输出格式偏好 Markdown，
    包含代码块时需要标注语言类型。

---

## 2026-06-04_21-15_qwerty
- **type**: project_rule
- **status**: ACTIVE
- **tags**:
  - Python
  - 代码规范
  - 缩进
- **created_at**: "2026-06-04T21:15:00+08:00"
- **updated_at**: "2026-06-04T21:15:00+08:00"
- **access_at**: "2026-06-04T21:15:00+08:00"
- **access_count**: 0

    Python 文件统一使用 4 空格缩进，禁止使用 tab 字符。
    每行代码长度不超过 120 字符。
```

**格式规则**：

| 元素 | 说明 |
|------|------|
| 文件级 frontmatter | 记录文件元信息：`date`（文件日期）、`scope`（作用范围）、`memory_count`（本文件包含的记忆条数） |
| H1 标题 | `# {date} 记忆记录 ({scope})`，文件级标题 |
| H2 标题 | `## {memory_id}`，每条记忆的 ID，作为唯一锚点 |
| 记忆元数据 | 以 `- **{key}**: {value}` 格式的 YAML-like 键值对列表，紧跟 H2 标题 |
| 记忆正文 | 元数据区域后空一行，正文每行以 **4 空格缩进**开头。此缩进由 `MemoryStore` 写入时自动添加、读取时自动去除，用于防止正文中的 `## ` 或 `---` 被误解析为记忆分隔符 |
| 记忆分隔 | 使用 `---` 水平线分隔相邻的两条记忆（最后一条记忆之后无需分隔线） |

**解析规则**：
1. 按 `## ` 分割出每条记忆的区块（正文中已被缩进的 `    ## ` 不会被误分割）
2. 每个区块中，H2 标题行提取为 `id`
3. 紧随 H2 的键值对行（以 `- **` 开头）解析为元数据
4. 键值对区域之后、下一个 `## ` 或文件末尾之间的内容为记忆正文
5. 正文每行去除前导 4 空格缩进后还原为原始 Markdown 内容

> **注意**：
> - `memory_count` 字段为**仅供参考的缓存值**，真实记忆条数以解析出的 H2 区块数量为准。`rebuild_index` 时应重新计算并修正该值。
> - `tags` 在文件中以 YAML 列表格式存储（每行 `  - tag_value`），可包含任意字符（包括逗号、空格），比逗号分隔格式更安全。
> - `session_id` 仅出现在 `scope=session` 的记忆记录中。该值由 `MemoryExtractor` 在提取时从当前会话上下文获取，随 `MemoryRecord` 一起传入 `MemoryManager.create()`。

### 3.3 记忆 ID 生成规则

```
ID = {date}_{time}_{random6}

其中:
  date       = YYYY-MM-DD          (创建日期)
  time       = HH-MM               (创建时间，精确到分钟)
  random6    = [a-z0-9]{6}         (6位随机小写字母数字组合)
```

**示例**：`2026-06-04_20-29_asdfgh`

使用 Python 标准库生成：
```python
import secrets
import string

def generate_memory_id() -> str:
    from datetime import datetime
    now = datetime.now()
    date_part = now.strftime("%Y-%m-%d")
    time_part = now.strftime("%H-%M")
    alphabet = string.ascii_lowercase + string.digits
    random_part = "".join(secrets.choice(alphabet) for _ in range(6))
    return f"{date_part}_{time_part}_{random_part}"
```

### 3.4 数据完整性

- **文件系统为准（content 字段）**：每日 Markdown 文件是记忆的**内容（content）**的权威数据源（source of truth）。所有记忆内容持久化在这些文件中
- **SQLite 为准（统计字段）**：`access_at` 和 `access_count` 以 `memory_meta` 表为准。这两个字段更新频繁（每次检索命中都会更新），为避免频繁 I/O，**仅更新 DB，不同步回写 Markdown 文件**。Markdown 文件中的 `access_at` 和 `access_count` 作为创建/更新时刻的快照保留
- **FTS5 索引为镜像**：SQLite FTS5 是文件内容的索引镜像，设计为可重建。索引粒度细化到每条记忆（一条记忆对应 FTS5 中一行记录），而非每个文件
- **重建机制**：提供 `MemoryStore.rebuild_index()` 方法，遍历所有每日 Markdown 文件，解析每条记忆记录，重新构建 FTS5 索引。重建时采用**影子表切换**方案（见 §4.4），确保重建期间检索服务不中断
- **写入原子性**：写入当天文件时使用 `atomic_write`（先写临时文件 → `os.replace` 原子替换），防止写入过程崩溃导致文件损坏
- **文件级锁**：`MemoryStore` 维护以文件路径为粒度的 `threading.Lock` 字典，确保同一文件的**读取-修改-写入**复合操作互斥，防止多线程/多协程并发追加导致记忆丢失。锁在 `atomic_write` 完成后释放

## 4. SQLite FTS5 检索设计

### 4.1 数据库表结构

```sql
-- 开启 WAL 模式：允许读写并发，search_memory 读取不阻塞记忆写入
PRAGMA journal_mode=WAL;

-- 元数据表：存储结构化字段
CREATE TABLE IF NOT EXISTS memory_meta (
    id           TEXT PRIMARY KEY,
    type         TEXT NOT NULL,
    scope        TEXT NOT NULL,
    status       TEXT NOT NULL DEFAULT 'ACTIVE',
    tags         TEXT NOT NULL DEFAULT '',        -- JSON array string: '["tag1","tag2"]'
    session_id   TEXT,                             -- 关联的会话 ID，仅 scope='session' 时非空
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL,
    access_at    TEXT NOT NULL,
    access_count INTEGER NOT NULL DEFAULT 0,
    file_path    TEXT NOT NULL                     -- 相对路径，如 "user/2026-06-04.md"
);

-- 全文索引表：用于 FTS5 检索
-- memory_id 标记 UNINDEXED：仅用于 JOIN 关联，不参与全文索引，减少索引体积
CREATE VIRTUAL TABLE IF NOT EXISTS memory_fts USING fts5(
    memory_id UNINDEXED,
    tags,           -- 标签文本（空格分隔，用于 MATCH 检索）
    content,        -- 记忆正文
    tokenize='unicode61'      -- 支持中文/英文混合分词
);

-- 辅助索引
CREATE INDEX IF NOT EXISTS idx_meta_type ON memory_meta(type);
CREATE INDEX IF NOT EXISTS idx_meta_scope ON memory_meta(scope);
CREATE INDEX IF NOT EXISTS idx_meta_status ON memory_meta(status);
CREATE INDEX IF NOT EXISTS idx_meta_session ON memory_meta(session_id);
CREATE INDEX IF NOT EXISTS idx_meta_access ON memory_meta(access_at DESC);
```

### 4.2 写入与同步策略

**写入原则**：每次记忆创建/更新/删除时，同步维护 Markdown 每日文件与 SQLite 中的 `memory_meta` 和 `memory_fts` 表，使用 **SQLite 事务 + 文件级锁** 保证一致性。`MemoryStore` 维护一个 `_file_locks: dict[str, threading.Lock]` 字典，以文件相对路径为键，确保同一文件的读取-修改-写入复合操作互斥。

**创建新记忆的流程**：

```
1. 生成 memory_id: "{date}_{time}_{random6}"
2. 确定目标 Markdown 文件路径: {scope}/{date}.md
3. 获取文件级锁: lock = _file_locks[file_path]
4. BEGIN TRANSACTION (SQLite)
5. INSERT OR REPLACE INTO memory_meta (...)
6. INSERT OR REPLACE INTO memory_fts (memory_id, tags, content)
7. 读取目标 Markdown 文件（持锁状态下）:
   a. 文件不存在 → 创建新文件，写入 frontmatter + H1 + 第一条记忆
   b. 文件存在 → 解析已有内容，追加新记忆记录（H2 + 缩进后的正文 + ---）
8. 更新 frontmatter 中的 memory_count（仅供参考）
9. atomic_write: 先写 .tmp 临时文件 → os.replace 原子替换原文件
10. COMMIT (SQLite)
11. 释放文件级锁
```

**更新已有记忆的流程**：

```
1. 从 memory_meta 查询目标记忆的 file_path
2. 获取文件级锁: lock = _file_locks[file_path]
3. BEGIN TRANSACTION (SQLite)
4. UPDATE memory_meta SET updated_at = ?, ... WHERE id = ?
5. REPLACE INTO memory_fts (memory_id, tags, content)
6. 读取目标 Markdown 文件（持锁状态下），定位到对应 H2 区块，替换元数据 + 正文
7. atomic_write 写回文件
8. COMMIT (SQLite)
9. 释放文件级锁
```

**异常处理**：
- SQLite 写入失败：直接回滚，不修改 Markdown 文件
- Markdown 文件写入失败：回滚 SQLite 事务，保证两者一致
- Markdown 解析失败（文件损坏）：记录错误日志，依赖下次 `rebuild_index` 修正 DB 中的记录
- `atomic_write` 过程崩溃：临时文件残留不影响数据，下次写入时清理

### 4.3 检索 SQL

```sql
-- 基础检索：FTS5 全文匹配 + 元数据过滤
SELECT
    m.id,
    m.type,
    m.scope,
    m.status,
    m.tags,
    m.created_at,
    m.updated_at,
    m.access_at,
    m.access_count,
    f.content,
    fts_rank(memory_fts, 0) AS relevance   -- FTS5 相关度评分
FROM memory_fts f
JOIN memory_meta m ON f.memory_id = m.id
WHERE memory_fts MATCH :query_pattern      -- FTS5 全文检索表达式
  AND m.status IN (:status_filter)         -- 默认 ('ACTIVE',)，include_archived=true 时为 ('ACTIVE','ARCHIVED')
  AND (:type_filter IS NULL OR m.type = :type_filter)
  AND (:scope_filter IS NULL OR m.scope = :scope_filter)
ORDER BY
    CASE m.scope                              -- scope 优先级: session > project > user
        WHEN 'session' THEN 3
        WHEN 'project' THEN 2
        WHEN 'user' THEN 1
        ELSE 0
    END DESC,
    relevance DESC                            -- 再按 FTS5 相关度排序
LIMIT :limit;
```

**FTS5 查询构造**：
- `query` 包含单个关键词时：`"keyword"` （精确匹配）
- `query` 包含多个关键词时：`"keyword1" OR "keyword2" OR "keyword3"` （任一匹配）
- FTS5 特殊字符（`"`、`*`、`(`、`)`）做转义处理，防止语法错误
- `unicode61` 分词器对中文按字符 bigram 分词（如"中文回复" → `"中文" "文回" "回复"`），检索单个中文字符时可能匹配较弱，建议 query 使用 2 个以上中文字符组成的关键词

**降级检索路径**：当 FTS5 MATCH 查询无结果（`fts_rank` 全为 0）时，自动降级为对 `memory_meta.tags` 列的 LIKE 模糊匹配，确保在无精确全文匹配时仍能返回相关结果：

```sql
-- 降级查询（无 FTS5 匹配时使用）
-- 注意：memory_meta 不含 content 列，需 JOIN memory_fts 获取
SELECT m.*, f.content, 0.5 AS relevance
FROM memory_meta m
LEFT JOIN memory_fts f ON f.memory_id = m.id
WHERE m.tags LIKE '%' || :keyword || '%'
  AND m.status IN (:status_filter)
  AND (:type_filter IS NULL OR m.type = :type_filter)
  AND (:scope_filter IS NULL OR m.scope = :scope_filter)
ORDER BY m.access_at DESC
LIMIT :limit;
```

### 4.4 索引重建

采用**影子表切换**方案，确保重建期间检索服务不中断：

```python
def rebuild_index(self) -> dict:
    """遍历所有每日 Markdown 文件，逐条解析记忆记录，重建 FTS5 索引。

    重建期间 search_memory 始终可用（基于旧表检索，直到新表切换完成）。
    """
    # 1. 创建影子表（带 _new 后缀）
    #    CREATE TABLE memory_meta_new (...)
    #    CREATE VIRTUAL TABLE memory_fts_new USING fts5(...)
    #
    # 2. 遍历 user/, project/, session/, archive/ 四个目录
    #    对每个 {date}.md 文件:
    #      a. 解析 YAML frontmatter，获取 date, scope
    #      b. 按 '## ' 分割出每条记忆记录的区块
    #      c. 从每个区块中解析: id, type, status, tags, session_id, created_at, ... content
    #      d. 去除正文每行的 4 空格缩进前缀，还原原始 content
    #      e. INSERT INTO memory_meta_new (...)
    #      f. INSERT INTO memory_fts_new (memory_id, tags, content)
    #      g. 修正 memory_count = 实际解析到的 H2 区块数量
    #
    # 3. 在一个 SQLite 事务中完成切换（使用排他锁避免窗口期）:
    #    PRAGMA locking_mode = EXCLUSIVE;  -- 获取排他锁，阻塞其他读写
    #    BEGIN EXCLUSIVE TRANSACTION
    #    -- 此时所有检索操作等待，直到事务提交
    #    DROP TABLE IF EXISTS memory_fts;
    #    DROP TABLE IF EXISTS memory_meta;
    #    ALTER TABLE memory_fts_new RENAME TO memory_fts;
    #    ALTER TABLE memory_meta_new RENAME TO memory_meta;
    #    -- 重建辅助索引
    #    COMMIT
    #    PRAGMA locking_mode = NORMAL;     -- 恢复正常锁模式
    #    -- 排他锁期间检索调用会短暂阻塞（通常 < 100ms），返回正确结果
    #
    # 4. 记录日志：文件 N 个，记忆记录 M 条，成功 X 条，失败 Y 条
    # 5. 返回统计: {"files": N, "records": M, "success": X, "errors": [...]}
```

### 5.4 LLM 调用 search_memory 的典型场景

| 场景 | LLM 推理 | search_memory 参数 |
|------|---------|-------------------|
| 用户说"用中文回复" | 这是用户偏好，需要检索已有偏好确认是否已记录 | `query="中文回复 语言偏好", type="user_preference"` |

| 用户说"帮我回忆一下之前那个..." | 可能涉及较久远的记忆，需包含归档 | `query="<关键词>", include_archived=true` |

### 5.5 检索后处理

检索成功后，`search_memory` 工具自动更新命中的记忆元数据：

- **`access_at`**：更新为当前时间（仅更新 `memory_meta` 表，不同步回写 Markdown 文件，避免高频 I/O）
- **`access_count`**：自增 1（同上，仅更新 `memory_meta` 表）
- **唤醒机制**：如果记忆状态为 `ARCHIVED` 且被检索命中，自动激活为 `ACTIVE`。由于 ARCHIVED 记忆仍保留在 FTS5 索引中（见 §6.3），常规检索即可命中归档记忆。命中后，`MemorySearcher` 执行唤醒：
  1. 更新 `memory_meta.status = 'ACTIVE'`
  2. 从记忆 ID 中提取原始创建日期（ID 格式 `{date}_{time}_{random6}` 的前 10 位即为创建日期），推导原始文件路径 `{scope}/{date}.md`
  3. 将记忆区块从 `archive/{archived_date}.md` 移回原始每日文件
  4. 若归档文件在移出后为空，删除该归档文件

> **设计要点**：
> - `access_at` 和 `access_count` 的权威来源是 `memory_meta` 表。Markdown 文件中的这两个字段仅在创建/更新时写入，作为那个时刻的快照保留。`rebuild_index` 时不会丢失这两个字段（从 `memory_meta` 读取后与文件内容合并）。
> - 当检索无结果时（空列表），`search_memory` 返回 `[]`。Agent 应据此判断"没有相关历史记忆"，并自行决定是否继续当前任务或向用户询问更多信息。

## 6. 记忆生命周期管理

### 6.1 记忆创建（Create）

```
触发时机:
  - 每次 execute_turn 完成后，异步提取对话中的新记忆
  - 用户显式指令："记住这个""帮我记录一下"
  - 系统检测到重要的架构决策或 bug 修复

创建流程:
  1. MemoryExtractor (LLM) 从对话中提取潜在记忆
  2. 生成记忆 ID（基于当前日期时间）
  3. 判断 type / scope / tags / session_id（如适用）
  4. 去重检查（两步法）：
     a. **快速召回**：用 FTS5 在现有 ACTIVE 记忆中检索候选（`limit=3`），匹配 type + scope 相同、内容相关的已有记忆
     b. **精确判断**：对候选记忆做文本相似度计算（Jaccard 相似度 或 embedding 余弦相似度）
        - 相似度 > 阈值（如 0.85）：合并更新已有记忆（执行 §6.2 更新流程）
        - 否则：创建新记忆
  5. 定位目标文件: {scope}/{today_date}.md
     - 文件存在 → 读取并追加新记忆记录（正文自动缩进处理）
     - 文件不存在 → 创建新文件并写入第一条记忆
  6. 同步更新 FTS5 索引（INSERT INTO memory_fts + memory_meta）
  7. 标记为 ACTIVE 状态
```

### 6.2 记忆更新（Update）

```
触发时机:
  - 新提取的记忆与已有记忆高度相似（覆盖更新）
  - 用户纠正："不对，我之前说的是..."
  - 项目规范/架构决策发生变化

更新流程:
  1. 从 memory_meta 查询目标记忆的 file_path，定位到所属每日文件
  2. 解析 Markdown 文件，找到目标记忆的 H2 区块
  3. 替换该区块中的元数据键值对和正文内容
  4. atomic_write 写回文件
  5. 同步更新 FTS5 索引（DELETE + INSERT）
  6. 如果原状态为 ARCHIVED：
     a. 从记忆 ID 推导原始文件路径，将 H2 区块移回原 `{scope}/{date}.md`
     b. 若归档文件移出后为空，删除该归档文件
     c. 更新 memory_meta.status = 'ACTIVE'、memory_meta.file_path 指向原始文件
```

### 6.3 记忆归档（ARCHIVE）

```
触发条件（自动）:
  - session 范围的记忆：当前会话结束时，自动标记为 ARCHIVED
  - 其他范围记忆：access_count 很低 且 updated_at > 90 天前

触发条件（手动）:
  - 用户指令："这条记忆不用了，先归档"

归档操作:
  1. 从 memory_meta 查询目标记忆的 file_path，定位到所属每日文件
  2. 解析原文件，找到目标记忆的 H2 区块
  3. 从原文件中移除该记忆的 H2 区块（含分隔线），更新 memory_count
  4. 若原文件移除后无任何记忆记录，删除该空文件
  5. 将移除的区块追加写入 archive/{today_date}.md（按归档日期归入归档文件）
  6. 更新 memory_meta.status = 'ARCHIVED'、memory_meta.file_path 指向新的归档文件
  7. **保留 FTS5 索引中的记录**（不删除），更新 `memory_fts` 中的 content 为最新内容（如有变更）
  8. `search_memory` 默认过滤 `status='ACTIVE'`，常规检索不会命中归档记忆
```

> **策略选择**：归档记忆**保留在 FTS5 索引中**，`search_memory` 通过 `WHERE m.status = 'ACTIVE'` 默认过滤掉归档记忆。当用户显式检索归档记忆（如 `search_memory(query, type=..., scope=..., include_archived=true)`）或被定时任务扫描到时，可直接命中并触发唤醒（ARCHIVED → ACTIVE）。这样既避免了"删除后无法唤醒"的矛盾，又通过 status 过滤保证了常规检索的精准度。

### 6.4 记忆废弃（INVALID）

```
触发条件:
  - 用户明确标记："这条记忆是错误的""删掉这条"
  - 新记忆内容完全覆盖旧记忆（语义等同，内容更新）

废弃操作:
  1. 更新 memory_meta.status = 'INVALID'
  2. 从 FTS5 索引中删除（DELETE FROM memory_fts WHERE memory_id = ?）
  3. Markdown 文件中该记忆的 H2 区块保留不动（原位备查）
  4. 可选：在区块元数据中追加标记如 '- **status**: INVALID'
```

### 6.6 物理删除（Delete）

```
触发条件:
  - INVALID 记忆超过保留期限（如 30 天），由维护任务触发清理
  - 用户显式指令："永久删除这条记忆"

物理删除操作（不可逆）:
  1. 从 memory_meta 查询目标记忆的 file_path
  2. 获取文件级锁: lock = _file_locks[file_path]
  3. BEGIN TRANSACTION (SQLite)
  4. DELETE FROM memory_meta WHERE id = ?
  5. DELETE FROM memory_fts WHERE memory_id = ?  （若 INVALID 时已删除，此步跳过）
  6. 定位 Markdown 文件中的 H2 区块，物理移除该区块（含分隔线）
  7. 更新 frontmatter 中的 memory_count
  8. 若移除后文件为空，删除整个 Markdown 文件
  9. atomic_write 写回文件
  10. COMMIT (SQLite)
  11. 释放文件级锁
```

### 6.5 定时维护任务

```
维护频率: 每天执行一次（或在会话开始时惰性检查）

维护内容:
  1. 扫描所有 ACTIVE 记忆，检查是否需要归档
     - session 范围的记忆，若其 session_id 不等于当前活跃会话 ID → ARCHIVE（旧会话记忆自动清理）
     - 非 session 范围记忆，access_count < 阈值（30 天内 < 2 次）且 updated_at > 90 天前 → ARCHIVE
  2. 清理归档后变为空的每日文件（删除空文件，保持目录整洁）
  3. 清理 INVALID 记忆：Markdown 文件中的 INVALID 区块保留至少 30 天后物理删除
  4. 验证 FTS5 索引与文件系统的一致性（比对 memory_meta 记录数 vs 文件 H2 区块总数）
     - 一致：跳过重建
     - 不一致：触发 rebuild_index()（影子表切换，不中断服务）
  5. 输出维护日志：归档 N 条，唤醒 M 条，清理空文件 X 个，索引验证通过/触发重建
```

## 8. 上下文注入集成

### 8.1 注入策略

记忆按 `type` 分类，注入到不同的上下文构建层：

```
上下文构建层          注入的记忆类型
─────────────────────────────────────────
Layer 1 (System)     不加记忆（纯系统指令）
Layer 2 (Guard)      user_preference      ← 用户偏好影响意图理解
Layer 3 (Plan)       arch_design          ← 架构记忆辅助方案设计
                     project_rule
                     design_pattern
                     bug_pitfall          ← 避坑经验防止重复犯错
                     general_knowledge
Layer 4 (Execute)    不加记忆（执行层依赖工具）
```

### 8.2 注入时机

| 时机 | 触发 | 注入内容 |
|------|------|---------|
| 会话创建时 | `load_for_context()` | 所有 `user_preference` 类型 + 最近访问的 N 条 `arch_design` / `project_rule` |
| GuardAgent 意图分析后 | `search(query, type="bug_pitfall")` | 与当前意图相关的 bug 避坑记忆 |
| PlanAgent 方案设计时 | `search(query, type="arch_design")` | 与当前任务相关的架构决策记忆 |
| LLM 主动调用 | `search_memory` 工具 | Agent 根据实际需要灵活检索任意类型 |

### 8.3 格式化输出

注入上下文的记忆需格式化为 LLM 可理解的文本：

```
[用户偏好记忆 - ID:2026-06-04_20-29_asdfgh]
- 用户希望所有回复使用简体中文
- 代码注释使用英文，输出格式偏好 Markdown

[架构设计记忆 - ID:2026-05-28_09-12_zxcvbn]
- 项目采用三层编排架构：Guard → Plan → Execute
- 模块间通过 OrchestrationState 传递状态
- 禁止跨层直接调用
```

## 9. 数据迁移方案

### 9.1 迁移范围

从旧格式（v1）迁移到新格式（v2）的数据范围：

| 旧格式 | 新格式 |
|--------|--------|
| `user_profile.md` 中的每条偏好 | 多条 `type=user_preference, scope=user` 的记忆 |
| `topic/{slug}.md` 中的每条条目 | 多条 `type=arch_design/bug_pitfall/...` 的记忆（按内容推断 type） |
| `index.json` | 废弃，由 FTS5 索引替代 |
| `archive/` 中的归档文件 | 迁移到新 `archive/` 目录，`status=ARCHIVED` |

### 9.2 迁移脚本

```python
# migration.py

def migrate_v1_to_v2(old_dir: Path, new_dir: Path) -> dict:
    """将 v1 格式的记忆迁移到 v2 格式。

    迁移后的记忆按 scope 分目录存放，同一天迁移的记忆归入同一个 {date}.md 文件。

    Returns:
        {"migrated": N, "skipped": M, "errors": [...]}
    """
    stats = {"migrated": 0, "skipped": 0, "errors": []}
    daily_buffers: dict[tuple[str, str], list[MemoryRecord]] = {}
    # key: (scope, date_str) → value: 该天该 scope 的记忆记录列表

    # 1. 迁移 user_profile.md → 多条 user_preference 记忆
    profile = load_old_profile(old_dir / "user_profile.md")
    for category, items in profile.preferences.items():
        for item in items:
            record = MemoryRecord(
                id=generate_memory_id(),
                type="user_preference",
                scope="user",
                status="ACTIVE",
                tags=extract_tags(item.content, max_tags=3),
                content=f"[{category}] {item.content}",
                ...
            )
            key = (record.scope, record.id[:10])  # 提取日期部分
            daily_buffers.setdefault(key, []).append(record)

    # 2. 迁移 topic/*.md → 按内容推断 type
    for topic_file in (old_dir / "topic").glob("*.md"):
        topic = load_old_topic(topic_file)
        for entry in topic.entries:
            inferred_type = infer_type_from_content(entry)
            record = MemoryRecord(
                id=generate_memory_id(),
                type=inferred_type,
                scope="project",
                status="ACTIVE",
                tags=topic.keywords[:3],
                content=format_entry_as_content(entry),
                ...
            )
            key = (record.scope, record.id[:10])
            daily_buffers.setdefault(key, []).append(record)

    # 3. 按 (scope, date) 分组写入每日文件
    for (scope, date_str), records in daily_buffers.items():
        write_daily_file(new_dir / scope / f"{date_str}.md", records)
        stats["migrated"] += len(records)

    # 4. 迁移 archive/ → status=ARCHIVED
    ...

    return stats
```

### 9.3 迁移后验证

1. 对比迁移前后记忆总数是否一致
2. 抽样检查迁移后的 Markdown 文件内容完整性
3. 运行 `rebuild_index()` 验证 FTS5 索引构建成功
4. 执行几条测试检索，验证检索结果合理

## 11. 附录

### 11.1 与旧版设计的关键差异对比

| 维度 | 旧版（v1） | 新版（v2） |
|------|-----------|-----------|
| **记忆粒度** | 以"主题"为组织单元，多条经验耦合 | 每条记忆独立存储，粒度细化到单条 |
| **存储格式** | Markdown（每主题一个文件） + JSON 索引 | Markdown（每天每 scope 一个文件，内含多条记忆） + SQLite FTS5 |
| **检索方式** | 关键词匹配 + 时间衰减 | FTS5 全文检索 + scope 优先级排序 |
| **检索调用** | MemoryManager.search() 被动调用 | search_memory 工具，LLM 自主决定 |
| **状态管理** | 无（仅通过时间戳判断过期） | ACTIVE / ARCHIVED / INVALID 三态机 |
| **类型体系** | 用户画像 + 主题记忆（双层） | 六种类型 + 可扩展（user_preference 等） |
| **访问追踪** | 无计数 | access_at + access_count |
| **作用范围** | 无 | user / project / session 三级 |
| **索引重建** | 不支持 | MemoryStore.rebuild_index() |

### 11.2 安全与权限考量

- **session 记忆隔离**：`scope=session` 的记忆携带 `session_id` 字段，`archive_session_memories(session_id)` 通过该字段精准定位，不会误归档其他会话的记忆。检索时也可按 `session_id` 隔离
- **project 记忆隔离**：不同项目的记忆通过 `scope=project` 隔离，需配合项目标识符使用
- **SQLite 注入防护**：FTS5 查询使用参数化查询，避免 SQL 注入风险。`query` 参数中的特殊 FTS5 字符（如 `"`、`*`、`(`）做转义处理
- **文件路径安全**：ID 生成使用 `secrets.choice` 安全随机数，防止路径遍历攻击。文件路径由 `scope` 目录 + `{date}.md` 拼接，`date` 部分由 `datetime.strftime` 生成，不包含用户输入

### 11.3 性能预估

| 操作 | 预期耗时 | 说明 |
|------|---------|------|
| 创建记忆（追加到每日文件 + 写 FTS5） | < 15ms | 追加新记忆记录到每日文件 + 单条 FTS5 INSERT |
| 更新记忆（原地替换每日文件中的 H2 区块 + 写 FTS5） | < 20ms | 解析文件定位区块 + atomic_write 写回 + FTS5 DELETE + INSERT |
| search_memory 检索 | < 5ms | FTS5 全文索引，数据量 < 10000 条 |
| rebuild_index（100 个每日文件，3000 条记忆） | < 3s | 批量解析多记录文件 + 批量 INSERT |
| 维护任务（检查 1000 条） | < 500ms | 查询 memory_meta，条件判断 + 少量 UPDATE |
